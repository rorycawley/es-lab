# Event Sourcing Laboratory

A sequence of small labs that build up to an event-sourced system in Clojure, one idea at a time.

Influenced by [Do-It-Yourself: Event-Sourcing](https://www.youtube.com/watch?v=VSS_Q0Rf50E).

## How the labs work

Each lab is a self-contained Clojure project introducing exactly **one** idea, and the README carries most of it. Read the README, then read the tests to see the idea asserted.

Lab 0 starts with executable business rules in a pure domain namespace and contrasts them with a persistence-shaped model. Labs 1–5 then isolate the three message shapes, their identities and their cardinalities. Lab 6 introduces the first event fold, and from lab 8 the event-sourced example separates into domain, store and application namespaces because keeping those concerns apart is itself one of the things being taught.

The running example through Lab 29 is an Ice Cream truck selling flavours.
Lab 30 deliberately changes domain to a corporate Registry because multilingual
legal-name lookup needs real French, German, and Italian names rather than
translated ice-cream labels.

Labs build on each other in order, and each one points to what follows; later labs link back whenever they spend an earlier idea. Changes are never silent: when a later lab changes a shape introduced earlier, the earlier examples are brought forward and the later lab preserves the old shape where history requires it, then explains what changed its mind.

**Lab 0 is the one with no events in it.** Before a fact is recorded there is a model, and if that is wrong nothing above it can be right. A model is a *reduction* — a toy train is not a small real train, and what its builder threw away is what makes it useful — so the lab turns that into a criterion you can run: **an attribute that cannot change any answer is not part of the model.** Everything true about a truck one morning in August, varied across every plausible value, and not one answer moves; nine attributes come out and `{:stock …}` remains. Then the same two business rules written the way a framework's `models/` folder would have you write them — a record whose fields are a table's columns, methods that read and write, and `snake_case` leaking upward into the thing the business calls its truck. It is not a straw man and it works. The bill is in the tests: asking the domain model a question costs a map literal and asking the persistence model costs a store, a row and an id; ask twice and only one of them answers the same way, because the other has a clock in it. And the expensive one, which turned out to be mechanically checkable — `(is (nil? (resolve 'lab0.models.truck/sellable?)))`. The rule is not missing, it is *in there*, as an `if` between a read and a write, with nowhere to put a name. A rule with no name cannot be pointed at, tested alone, or read back to the person who asked for it.

**Labs 1–3 build the vocabulary.** Three shapes that look almost alike and mean entirely different things:

```text
COMMAND              please do this           may be refused
DOMAIN EVENT         this happened            already true, inside the domain
INTEGRATION MESSAGE  telling someone else     a contract across a boundary
```

Most of the difficulty in an event-sourced design is keeping these three straight. Collapsing any two of them is the usual way it goes wrong.

**Lab 4 separates identity from its identifier.** In Rich Hickey's terms, identity is the logical continuity joining immutable state values over time; a UUID is the value used to refer to it. A hospital with two John Smiths makes the need visible, while events add a wrinkle: an event does not change state, so its id names one immutable fact. Commands, facts and message envelopes need distinct identifiers for distinct retry boundaries. The sender reuses a command id, the event-recording application supplies a fact id before append, and a publisher creates a message id for each new envelope. The lab also compares UUIDv4 with UUIDv7's timestamp-prefixed index locality, without treating v7 as event ordering, and keeps clock reading, randomness and identifier allocation out of pure functions.

**Lab 5 counts.** The first four labs show one command, one event, one message, which quietly implies matched sets. One decision records zero, one or several event proposals; one publication decision exposes zero, one or several message proposals. Zero events does not alone distinguish a refusal from an accepted no-op, and a refusal that matters to the business may itself earn an event even when the truck's state fold ignores it. These are fan-out function shapes, not a universal ban on projections or processes combining many inputs; causation and correlation arrive in Labs 10 and 11.

**Lab 6 is the first event-sourced behaviour.** `evolve` folds one event into state; `reduce` does the rest. The event history is the source of record, while current state is derived and may later be cached as a disposable snapshot. `evolve` does not re-judge supported recorded facts — refusing a proposed action is `decide`'s job — but it handles deliberately irrelevant events explicitly and rejects event types whose semantics the reader does not know.

**Lab 7 says which events to fold.** With two trucks in one log, "the events" stops being well defined — folding all of them returns a plausible number that answers a different question. `:stream/id` names the aggregate history; `:stream/version` orders it and supplies the compare-and-append condition. The lab models that contract with immutable values; a real store must enforce the version check and write atomically so two tills cannot sell the same last cone.

**Lab 8 closes the decision loop.** `decide` takes a valid command and folded state and returns zero, one or several event proposals; it is where context-dependent business rules may refuse while the answer is still open. The application boundary identifies those proposals before append, while the store assigns stream versions. Expected version comes from the exact history folded, and the immutable example models the atomic compare-and-append contract a production store must enforce.

```text
1. read    the stream        (lab 7)
2. fold    it into state     (lab 6)
3. decide  what happened     (lab 8)
4. append  at expected+1     (lab 7)
```

**Lab 9 adds the read side.** A projection is the same fold pointed at a different question—usually across streams and allowed to lag, but still correct through its checkpoint. `:event/position` supplies a global cursor that may contain gaps; a projector compares positions rather than guessing the next integer. State and checkpoint must persist atomically, and incremental catch-up equals rebuilding from zero when the required facts remain retained, readable and reproducible.

**Lab 10 makes the system react to itself.** A policy owns the coordination rule between a fact and a request — *whenever a truck runs out, ask for twenty more* — while the target aggregate's `decide` function remains the authority for its state-dependent invariants. Known irrelevant events are explicit and unknown semantics fail rather than being checkpointed silently. The application identifies event proposals and records causation before append; a command id derived from the triggering event makes at-least-once redelivery recognisable. For this policy, whose command always emits an event, causation supplies a narrow deduplication shortcut; Lab 20 adds the command ledger required for the general zero-event case.

**Lab 11 gives the policy a memory.** A process manager is the decider shape once more — `state → now → [command]` — and owns the workflow rules for a multi-step transfer without copying either truck's invariants. This implementation reconstructs its state from domain facts sharing a correlation id across two aggregate streams; process managers may instead persist their own state or stream. It also introduces a second driving edge: a timer must wake active work after the event checkpoint advances, because injecting a clock value alone cannot make a timeout run. The runner distinguishes the donor's named business refusal from unexpected failures, and the application identifies facts and attaches causation and correlation before the store assigns versions and positions.

**Lab 12 sends the first integration message.** Recording a fact and publishing across a network are independent writes, so the relay publishes before checkpointing and recipients must tolerate a republish. A retained event log can be the relay source when outgoing contracts remain deterministically derivable; a transactional outbox is still required when the exact payload, recipient, version or message identity must be frozen with the domain write. Contracts are addressed, unknown event semantics fail before checkpointing, and envelopes carry immediate causation plus propagated correlation. The customer consumer deduplicates per recipient and fact rather than by the newly created envelope id, while stating that a production effect needs a durable inbox transaction rather than an in-memory `:seen` set.

**Lab 13 faces time passing.** Historical representations are preserved and adapted on read; physical migration remains a controlled last resort with retained originals and provenance, not a routine rename. Strict per-type ladders walk supported old shapes forward one version at a time while rejecting unknown types, malformed or future versions, missing rungs, and upcasters that alter the recorded envelope. The domain sees no schema versions. Changes to how a fact is written get upcast; changes to what it means get a new event type, because mislabeling a meaning change silently corrupts every historical total. An append-only compatibility corpus proves both representation and meaning remain readable.

**Lab 14 compensates a step that already committed.** Give the truck a capacity and lab 11's transfer breaks in the interesting place: the donor has given ten cones up and the empty truck has no room for them. One local transaction cannot roll back that independently committed fact, so compensation is a further *business* action with its own command and event; the log holds the attempt, refusal and return. The fleet total is 49, then 39, then 49 again. A return can itself be refused, leaving the process in `:needs-attention` for an operator-facing adapter to surface. Strict folds reject unknown semantics, the reactor subscribes only to transfer conversations, and active work remains eligible for timer wake-ups after checkpointing.

**Lab 15 minimises and protects personal data.** Routine deletion of one event would violate this store's contiguous-history contract, though controlled redaction or migration may still be required by a system's real obligations. Sales avoid repeating names and email, but their opaque customer id is pseudonymous rather than automatically anonymous. A deliberately retained personal field is sealed at the application edge under a non-replaceable per-subject key; the pure domain knows no cryptography, persistence never receives plaintext, and strict readers distinguish a missing key from corruption or an unsupported envelope. The after-erasure model yields `:personal/erased` while retained sales facts still fold, but projections, recipients, backups and escrowed keys require their own coordinated purge. The lab demonstrates an architectural technique—not GDPR compliance or verified key sanitisation.

**Lab 16 asks where the aggregate boundary goes.** It states the invariant precisely: the depot must never issue stock it does not hold. One fleet stream can debit the depot and credit a truck atomically, but five overlapping sales on different trucks create four optimistic conflicts—not business refusals. Per-truck streams remove that coupling but Design B omits the depot rule entirely. Design C gives the shared stock its own stream: depot issues serialize where the invariant lives, truck sales do not, and the setup records both sides instead of manufacturing stock. The deterministic simulation fixes overlap to expose the boundary's contribution; real conflict rates still depend on workload and transaction duration. Strict folds reject unknown semantics, the application identifies facts before persistence, and Vernon's guidance remains a set of transactionally informed rules of thumb rather than a partitioning formula.

**Lab 17 caches the fold.** A snapshot changes replay cost, never the authoritative answer—delete every one and a full fold still works. It records the stream version and the *fold* version, because changing `evolve`'s state shape can invalidate cached state without changing any event. State and stream position must come from the same read or a concurrent append can be skipped; impossible positions are rejected. Those checks detect compatibility mistakes, not arbitrary byte corruption, so replaceability is not permission to trust bad cache data. Reading history in the wrong order double-counts, stale fold versions are refreshed immediately, and derived snapshots normally stay off the append's critical path. Lab 9's projection uses the same state-plus-cursor pattern but is a query model over a feed, not an aggregate snapshot.

**Lab 18 asks what was true last Tuesday.** A cone sold on the 3rd and recorded on the 6th makes “how much stock on the 5th?” two different questions: what was known at the transaction-time cutoff and what current evidence says was valid then. A correction happens now but can explicitly take effect on the original sale date; it names the sale rather than pretending the correction itself occurred in the past. This stock projection is additive, so effective-time selection works here—it is not permission to date-filter and reorder an arbitrary aggregate history. Persistence owns `:recorded-at`; the application owns fact identity and occurrence time. Re-running a decision needs the original command, its exact input version, every other decision input, and the executable historical rules. A rules number is only a pointer, and unexpected failures must not be relabelled as business refusals.

**Lab 19 makes persistence real.** The technology-independent decision model remains outside a Postgres 18 adapter, but the boundary has costs. JSONB has no keyword value type, so stored domain values use an enforced JSON-shaped contract while known envelope UUIDs are restored at the adapter. Event identity and occurrence time belong to the application; persistence assigns stream coordinates, while Postgres supplies global position and transaction-start `:recorded-at`. A stream-head compare-and-set rejects stale **and future** expected versions—something a unique event constraint alone cannot do—and eight real writers prove one winner plus seven typed concurrency conflicts. Exact identified-batch retries are idempotent, conflicting id reuse is distinct, and a failed later insert rolls back the whole batch and head. Finally, a `BIGSERIAL` value is allocated before commit visibility, so a naive checkpoint can skip an earlier transaction forever; the `pg_snapshot_xmin` reader closes that gap by withholding rows above the settled transaction boundary and accepting the resulting latency.

**Lab 20 delivers between modules.** Lab 12 argued the transactional outbox against an in-memory vector, where the failure it prevents cannot occur; with lab 19's transactions the argument can be spent. A command's events, its ledger row and its outgoing messages commit together. The ledger closes lab 10's hole by recording a valid command even when it legitimately emits no events, and distinguishes an exact retry from command-id reuse. Across a boundary the relay must publish and then mark, so at-least-once survives the outbox and the recipient needs an **inbox**. Inside one database, an atomic inbox claim can share a transaction with a local database effect and the outbox mark. That gives an exactly-once local effect—not general exactly-once delivery, and not a guarantee for email, payments or other remote side effects.

**Lab 21 gives it a shape, and makes it run.** [Lab 0](lab0) argued the principle and asserted it for one namespace; twenty labs then obeyed it by hand with nothing checking the parts lab 0 could not see — `decide`, `evolve`, `react` and `announce` were always pure, and labs 4 and 11 had already argued that clocks and id generators are effects. Drawing on Ian Cooper's account of Clean Architecture, this lab puts the business use cases at the centre and makes frameworks, persistence, clocks and identity mechanisms details at the edge. The four driven ports invert those dependencies; the ordinary application functions form the driving use-case surface; Component chooses concrete adapters only in the composition root. The persistence port preserves Lab20's real transaction boundary: stream-head compare-and-set, command ledger, facts and outgoing messages are one atomic outcome in both memory and PostgreSQL, rather than separate `append` and `enqueue` calls. Its testing strategy follows the same boundary: fast behaviour tests drive the public use cases with in-memory fakes, focused unit tests exercise pure domain rules directly with values, a neutral contract suite proves memory and Postgres honour the driven ports, and deliberately structural fitness tests enforce the inward dependency rule without pretending to be business regressions. The lab also preserves the decomposition warning: business capabilities choose the modules first, while technical layers selectively protect each module internally. And `bb demo` prints a day in the life of the truck — the first thing in the repository that starts.

**Lab 22 validates at the edge.** Lab 2 drew the line between context-independent *validation* and context-dependent *business rules*, and nothing implemented the first half. Building on Lab 21's existing use-case surface and atomic command outcome, an intake adapter validates the raw message before allocating command and correlation ids or constructing the internal command; Malli remains at that boundary and the pure domain remains free of it. The lab's spine is one assertion: a command can be perfectly well-formed and still correctly refused, and only one of those two answers can change without the command changing. Commands are validated **closed**, while known event schemas remain field-tolerant; unknown event semantics still fail in consumers. Schema-driven decoding is reserved for inherent JSON losses—causation and correlation UUIDs in the metadata envelope—rather than manufacturing a UUID-valued routing field in domain data. Only the named sold-out rule becomes `:refused`; concurrency, identity and infrastructure failures propagate instead of masquerading as business outcomes.

**Lab 23 puts it behind HTTP.** Reitit, ring and jetty appear in exactly two namespaces — the driving adapter and the composition root — and a fitness test fails the build if they spread. Routes name the *act*, Stripe-style: `POST /v1/sales`, not `PUT /v1/trucks/{id}`, because a PUT that changes status looks identical to every other PUT and carries no intent to audit or enforce. Lab 2's two kinds of rejection become **400** and **422**, with a test showing the 422 turning into a 200 once state changes while the 400 stays a 400 forever. A bidirectional check keeps the endpoint list and the command vocabulary the same list. And a ring handler being a function from a map to a map means the whole web layer is tested without a socket — bar one test that starts Jetty to prove there is one.

**Lab 24 asks who is calling.** It drives a real OIDC provider — `mock-oauth2-server`, which lives in `dev/` because an identity provider is a dependency of your tests and never of your application — and finds that authorisation is four things, not one. ADR-0020's layers land in four places the repository already built: role checks at the door beside the schemas, ownership inside `decide` where the state is, and response shaping in the query adapter. The two gates differ in *reachability*, which is the argument for having both: a policy issuing commands never passes the door, so a rule that matters has to live where nothing can go around it. The lab's best find is that **authority does not propagate** — correlation continues through the conversation, but the customer who bought the last cone did not authorise the restock, so its actor is stamped rather than inherited. Lab 1's warning about never storing a credential finally gets a test, and lab 22's closed external schemas stop a client from naming its own actor before internal identity exists. Actor values remain JSON-shaped strings while causation and correlation UUIDs are restored from the declared metadata schema. The actor is also part of command-ledger identity, so facts, the audited retry record and outgoing messages commit atomically and a command id cannot be replayed under somebody else's identity.

**Lab 25 turns the architecture ninety degrees.** Lab 21 made use cases central but warned that technical rings do not decompose a whole system. Catalog and Ordering now become explicit business modules, and each command, query or message consumer is a vertical slice containing its request shape, handler, SQL and response. The modules remain one deployment while Postgres gives them separate schemas and login roles; tests prove either role is denied read and write access to the other's tables. Catalog atomically commits command identity, today's price and a correlated public message through an outbox. The payload carries the stable price-change fact id, while each envelope has its own delivery id; Ordering atomically claims the fact in an inbox and owns its local price copy. Exact retries return the captured outcome, republishing the fact in a new envelope remains harmless, and identifier reuse with different intent is a collision. Today's catalog price and the price captured on an old order are deliberately duplicated because they mean different things. Integration tests exercise whole slices against Postgres, pure rules retain plain unit tests, cross-cutting validation and observation wrap handlers, and architecture fitness functions prevent calls around the public contracts or access to database handles. It is a safe extraction boundary, not an instruction to extract.

**Lab 26 adds the other kind of record.** The event log says what the business did and keeps it forever; telemetry says what the machine did and discards it in a fortnight, and REFERENCE.md has been holding the rule — *don't merge them* — since before there was a lab for it. Lab 25's `observation` behaviour, which put a keyword in an atom, becomes OpenTelemetry through clj-otel: a log emitted inside a slice's span carries that span's trace and span id, so a log line and a span are two views of one event rather than two piles joined by timestamp. Logback is bridged rather than replaced, because OpenTelemetry Java deliberately ships no logging API for applications. Catalog's price change, the relay's publish and Ordering's inbox write become **one trace across three separate commits**, and only because the W3C `traceparent` was frozen into the outbox row inside the price-change transaction — lab 12's argument applied to the context that explains the write. Minting it at relay time would name the relay's trace instead, and a batching relay has to degrade to span links rather than one parent. The trace id is still not the correlation id: one is sampled and expires, the other must answer a business question years later, and the inbox persists exactly one of them. A refused command is a *successful* span with an outcome attribute — lab 23's 400-versus-422 arriving at span status — while only the machine failing sets `ERROR`. The expensive find is that **telemetry is a data-protection surface**: lab 15's crypto-shredding cannot reach a customer's email sitting in a vendor's retention window, so attributes are a per-slice allow-list and a test sweeps every span name, attribute, event and log body for the address, including on the paths where debugging usually leaks it. Metrics count machine behaviour and are deliberately not asked how many prices changed, because sampling is a feature there and a defect in a business number.

**Lab 27 finds something.** Twenty-seven labs fetch rows by primary key; the moment someone types words into a box the conversation turns to a second datastore, and this lab is the argument for having it later. A search index is a [lab 9](lab9) projection with a different data structure — derived from retained source text, disposable, rebuildable — and the schema says so in DDL: a `GENERATED ALWAYS AS … STORED` `tsvector` that no trigger and no application code ever writes. Postgres refuses the one-argument `to_tsvector` there, and that refusal makes `'english'` part of the index's identity, which is [lab 17](lab17)'s fold version arriving in a new place: change the configuration and every stored vector is stale though no row changed. `LIKE` fails twice over — it matches letters rather than words, and forbidden to scan a 50,000-row table it scans anyway, because no index exists that it could ever use. That last claim is structural where a query plan is statistical, which is the difference the tests are built on. `websearch_to_tsquery` is the one parser that cannot raise on user input; `setweight` makes a product *called* pistachio outrank one that mentions it, and ranking changes order rather than truth, so it is not a business rule in [lab 0](lab0)'s sense. Trigrams answer the typo that is the real reason people leave, and answer it as `:did-you-mean` rather than as a result. Each module searches only what it owns — no shared index, no lag, no second copy — and the stated cost is that one search box over two owners returns two lists and can never return one. `customer_email` is the field that must not be searchable, because a trigram index over an address undoes labs [15](lab15), [24](lab24) and [26](lab26) at once.

**Lab 28 crosses the process boundary.** A remote call can fail before the far side acts or after it acts but before the answer returns, and those cases are indistinguishable here. The fallacies of distributed computing become executable failure modes: bounded retries answer an unreliable network, one deadline covers all attempts, a circuit breaker stops making a provider's outage worse and later probes its recovery, and a signed, fresh webhook is verified before its bytes are believed. The mechanisms do not manufacture safety. Stripe accepts a payment id as an idempotency key, so an ambiguous charge can be retried; SendGrid has no equivalent, so only a rate limit that proves rejection is repeatable. Stable identity is committed before the remote effect, concurrent workers converge on the winning key, callbacks and synchronous answers converge through a database constraint, and poison outbox messages are dead-lettered without blocking healthy work and can be manually revived. Ports and pure anticorruption layers isolate two genuinely heterogeneous provider contracts without pretending they make the guarantees equal. Fake providers on real sockets, real Postgres, and behavior tests make the distinction observable. Bandwidth and transport cost remain explicitly unmodelled; reconciliation remains the next unanswered reliability problem.

**Lab 29 publishes beyond the modular monolith.** Internal integration events remain facts routed between known modules; WebSub begins at the external boundary, where a topic is a URL whose current representation changed. Catalog facts fold into a deliberately public projection, and subscribers converge by fetching that representation rather than reconstructing a log. The hub verifies callback ownership before the first delivery so it cannot be used as an amplification service, bounds subscriptions with leases, signs each body with the subscriber's secret, and drops a persistently failing subscription. Fan-out becomes one durable delivery per consumer, so one subscriber cannot share another subscriber's retry or dead-letter state. WebSub remains an adapter: business modules know their contracts and never know the publication protocol.

**Lab 30 treats multilingual names as several projections of one legal value.** A Registry module preserves the NFC filed name and structures the legal form separately, then lets PostgreSQL derive a case-folded exact key, an accent-and-punctuation-folded trigram key, and a `tsvector` analyzed under French, German, and Italian together. The lookup API is an explainable cascade—registration number or EUID, exact name, prefix, phrase, then strict-word fuzziness—and refuses to send one- or two-character queries into the trigram rung. PostgreSQL is initialized with `PG_UNICODE_FAST`, because the default container locale does not fold `ß` to `ss`; tests also correct the source guide by proving that PostgreSQL 18.4 still marks `unaccent` stable while the schema's immutable wrapper is an explicit rebuild promise. Legal-form suffixes are removed at the query edge and rendered in the UI language. German Snowball cannot split compounds, so a pure, versioned word-list fallback derives searchable components and exposes its incompleteness rather than hiding it. Thirty tests exercise the public Registry API, the pure splitter, generated-column rebuilds, Unicode behavior, and actual B-tree and GIN plans against PostgreSQL 18.

## Keeping it honest

Thirty-one labs written in sequence drift. A forward pointer outlives the lab it named; a docstring says *copied from lab 8, unchanged* about a file that has since changed; a prerequisites list written when only one lab needed Docker. Two manual audits of this repository found the same failure mode both times, and most of it was mechanically checkable.

```bash
bb audit      # consistency checks across every lab and document
bb test-all   # every lab's suite, in order
```

`bb audit` verifies that every link and heading anchor resolves, that each lab's *What's next* names the lab that follows, that a file claiming to be another lab's **still is it** (by diff, ignoring the docstring), that the table and summaries here cover exactly the labs that exist, that every lab needing Docker is declared, and that `payload` stays reserved for a message in transit, never an event's own `:data`.

The repository's discipline is *assert it in a test*. Its prose was the one thing not asserted; now it is.

## Running a lab

Each lab has its own `deps.edn`, `bb.edn`, and pinned toolchain in `mise.toml`, so labs can drift apart without breaking each other.

```bash
cd lab1
bb help     # prerequisites and available tasks
bb all      # setup, check, test
bb test     # just the tests
```

Prerequisites are [mise](https://mise.jdx.dev) and [babashka](https://babashka.org); `bb setup` installs everything else the lab pins.

[Lab 19](lab19), [lab 20](lab20), [lab 21](lab21), [lab 22](lab22), [lab 23](lab23), [lab 24](lab24), [lab 25](lab25), [lab 26](lab26), [lab 27](lab27), [lab 28](lab28), [lab 29](lab29) and [lab 30](lab30) use Docker — they run against a real Postgres in a container. Labs 0–18 are pure Clojure and need nothing running, and `cd lab24 && bb serve` starts the whole system on `:3000` in memory — with an identity provider beside it on its own port — and no Docker at all.
